# Заметки: проблемы окружения и как я их решила

Журнал проблем, с которыми я столкнулась при настройке автотестов и CI.
Для каждой: симптом → как искала причину → причина → решение → вывод.

---

## 1. Негативные тесты блокировали общий аккаунт

**Симптом.** При первом прогоне упали `test_me_returns_current_user` (ERROR в фикстуре)
и UI-тест успешного входа. Ответ API: `423 Locked`,
`Account locked, too many failed attempts`.

**Причина.** `test_login_with_invalid_password` трижды вводил неверный пароль
для того же демо-аккаунта `customer@practicesoftwaretesting.com`, на котором
держатся позитивные тесты. После нескольких неудачных попыток магазин блокирует
аккаунт. Это защита от подбора пароля, а не баг.

**Решение.** Добавила метод `register()` в `ApiClient` и фикстуру `new_user`,
которая перед каждым тестом регистрирует нового пользователя со случайным email
через `POST /users/register`. Негативные проверки пароля идут на нём.

**Вывод.** Тесты не должны портить общие данные, от которых зависят другие тесты.
Тестовые данные лучше создавать на лету, под каждый тест.

> FAILED и ERROR — разные вещи: FAILED значит, что упала проверка в самом тесте,
> ERROR — что сломалась подготовка (фикстура) и тест даже не начался.

## 2. Таймауты из-за VPN

**Симптом.** Часть тестов упала с `ReadTimeout` (сервер не ответил за 15 секунд).
При повторном запуске все прошли.

**Причина.** Запросы шли через системный прокси VPN (`127.0.0.1:10809`), его
подхватывает `requests`. Первые запросы зависали на стороне сети, а не в коде.
Доказательство: тест с той же фикстурой регистрации в том же прогоне прошёл.

**Вывод.** Это flaky-падение из-за окружения. Сначала смотрю тип ошибки:
таймаут или сетевая ошибка — это окружение, `AssertionError` — логика.
Потом проверяю, воспроизводится ли падение.

## 3. Cloudflare на публичном стенде

**Симптом.** UI-тесты не находили поле email. В снимке страницы вместо формы
логина была проверка «Performing security verification». Без VPN сайт
не открывался вовсе (`Page.goto: Timeout 30000ms exceeded`).

**Причина.** Публичный сайт закрыт защитой Cloudflare от ботов. API живёт
на другом адресе, и у него такой проверки нет, поэтому API-тесты проходили.

**Решение.** Подняла магазин локально в Docker из официального репозитория
[practice-software-testing](https://github.com/testsmith-io/practice-software-testing)
и переключила тесты через `.env`:

```
BASE_URL=http://localhost:4200
API_URL=http://localhost:8091
```

**Вывод.** Тесты не должны зависеть от окружения, которое я не контролирую.
Своё окружение стабильнее, быстрее, и данные в нём можно сбросить в любой момент.

## 4. Порт 3306 занят локальным MySQL

**Симптом.** `docker compose up -d` упал с ошибкой
`ports are not available: ... 0.0.0.0:3306 ... bind`. Потом `artisan` ругался
на отсутствующий `vendor/autoload.php`.

**Причина.** На компьютере работает своя служба MySQL на порту 3306. Контейнер
базы не стартовал, и по цепочке не запустился контейнер `composer`, который
ставит PHP-библиотеки, отсюда и нет `vendor/`.

**Решение.** В `docker-compose.yml` магазина поменяла проброс порта базы
на `3307:3306`. Внутри Docker магазин по-прежнему ходит в базу через 3306,
3307 нужен только для доступа с компьютера.

**Вывод.** Вторая ошибка была следствием первой. Чинить нужно первую ошибку
в цепочке, а не последнюю.

## 5. Медленный первый запрос к локальному API

**Симптом.** Первый тест надолго «завис».

**Причина.** Первый логин после старта контейнеров занял около 9 секунд:
PHP загружает и кэширует файлы. Следующие запросы — около 0,25 секунды.

**Решение.** После `docker compose start` сначала открываю сайт в браузере
и только потом запускаю тесты.

## 6. CI: перенос окружения в GitHub Actions

На GitHub нет ни моего `.env`, ни моего Docker, поэтому CI ходил на публичный сайт,
и UI-тесты падали из-за Cloudflare (12 passed, 2 failed). Решила поднимать магазин
в Docker прямо внутри CI. Порядок запуска взяла из CI самого репозитория Toolshop.
Чтобы CI заработал, пришлось решить ещё три проблемы.

### 6.1. Гонка с контейнером composer

**Симптом.** 4 API-теста упали с `500`: `/brands`, `/products`, `/users/me`.
Логин и UI-тесты при этом прошли. Весь прогон тестов занял 3 секунды.

**Как искала.** В логах контейнеров увидела, что `composer` распаковывает
PHP-библиотеки (в том числе сам Laravel) в те же секунды, когда шли тесты.

**Причина.** Тесты стартовали раньше, чем окружение было готово. Пока composer
перезаписывал файлы, API отвечал 500 на часть запросов.

**Решение.** Шаг, который ждёт завершения контейнера `composer` и проверяет,
что он завершился с кодом 0.

### 6.2. Проверка готовности давала ложный результат

**Симптом.** Шаг прогрева API считал, что API готов, а тесты всё равно падали.

**Причина.** Прогрев проверял только `POST /users/login`, а логин работал.
Ломались другие эндпоинты.

**Решение.** Прогрев проверяет и логин, и `GET /brands`. Если API не готов,
шаг падает с понятным сообщением (`login=200 brands=500`) и печатает ответ
с ошибкой, до запуска тестов дело не доходит.

**Вывод.** Готовность нужно проверять по-настоящему, на нескольких разных
эндпоинтах, а не по одному удачному ответу.

### 6.3. Права на файлы: на Windows работает, на Linux нет

**Симптом.** Даже после ожидания composer `/brands` стабильно отдавал 500,
а логин работал.

**Как искала.** Посмотрела код магазина: `/brands`, `/products` и `/users/me`
используют кэш, а логин нет. Кэш файловый (`CACHE_DRIVER=file`), хранится
в `storage/`. Проверила права в своём локальном контейнере.

**Причина.** PHP в контейнере API работает от `www-data` с uid 1000.
Контейнер `composer` делает `chown -R www-data`, но в его образе `www-data`
имеет uid 82. На Windows Docker даёт папкам права `rwxrwxrwx`, поэтому
локально всё работало. На Linux права настоящие: PHP не мог записать кэш
и отвечал 500.

**Решение.** Шаг `chown -R www-data:www-data storage bootstrap/cache`
изнутри контейнера API, где uid правильный. Для диагностики при падении
CI теперь печатает `laravel.log` и логи контейнеров.

**Вывод.** «Работает у меня, но не в CI» — значит, окружения различаются.
Нужно найти, чем именно, и сделать так, чтобы ошибка в CI сама объясняла причину.

**Итог:** CI зелёный, все 14 тестов (API и UI) проходят против магазина,
поднятого с нуля на каждый прогон. Весь цикл — меньше 5 минут.



Postman: 404 вместо 422. Негативный запрос с количеством 0 получал 404 «Resource not found», хотя из pytest тот же запрос получал 422. Причина: Postman по умолчанию шлёт Accept: */*, и Laravel при ошибке валидации делал перенаправление (302) вместо JSON-ответа. Решение: заголовок Accept: application/json в pre-request-скрипте коллекции. Вывод: не ослаблять проверку под фактический результат, а искать, чем запросы отличаются.
