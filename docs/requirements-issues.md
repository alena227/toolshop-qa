# Вопросы и неточности в требованиях

Источник требований: Swagger API (`http://localhost:8091/api/documentation`)
и поведение сайта (`http://localhost:4200`).

Статусы: **Открыт** — ответа нет · **Уточнён** — ответ получен · **Баг** — заведён баг-репорт.

| ID | Где | Кратко | Статус |

| RI-002 | `POST /users/register` | Непонятно, зачем у регистрации ответ 401 | Открыт |
| RI-003 | `POST /users/register` | Разная максимальная длина имени и фамилии | Открыт |
| RI-004 | `POST /users/register` | Не указана максимальная длина пароля | Открыт |

## RI-001: Не описан код ответа при ошибке валидации

**Где:** Swagger, `POST /users/register`, раздел Responses.

**Что не так:** в документации перечислены ответы `201`, `400`, `401`, `403`, `409`.
Непонятно, что вернёт API, если данные не прошли валидацию: пустой email,
пароль без цифры, возраст меньше 18. Laravel обычно отвечает `422 Unprocessable Entity`,
но в списке его нет.

**Вопрос:** какой код ответа правильный при ошибке валидации и какой формат у тела ответа?

**Зачем это нужно:** без этого непонятно, что проверять в негативных тестах регистрации.

**Ответ по факту (автотесты):** API возвращает `422` с ошибками по полям,
например `{"dob": ["Customer must be 18 years old."]}`. В Swagger это не задокументировано.

---

## RI-002: Зачем у регистрации ответ 401

**Где:** Swagger, `POST /users/register`, раздел Responses.

**Что не так:** `401 Unauthorized` значит «пользователь не авторизован». Но регистрацию
по определению выполняет неавторизованный пользователь. К тому же у ответа `401`
в документации нет описания.

**Вопрос:** в каком случае регистрация возвращает 401? Или это ошибка в документации?

---

## RI-003: Разная максимальная длина имени и фамилии

**Где:** Swagger, схема `UserRequest`.

**Что не так:** `first_name` — до 40 символов, `last_name` — до 20. Неясно, это осознанное
решение или опечатка. Двойные фамилии и фамилии с приставками легко превышают 20 символов.

**Вопрос:** правильные ли это ограничения? Что увидит пользователь на сайте, если превысит лимит?

**Идеи для тестов (граничные значения):** имя 40 и 41 символ, фамилия 20 и 21 символ.

---

## RI-004: Не указана максимальная длина пароля

**Где:** Swagger, схема `UserRequest`, поле `password`.

**Что не так:** указан только минимум (`minLength: 8`) и правило «заглавная, строчная,
цифра и спецсимвол». Максимальной длины нет.

**Вопрос:** есть ли ограничение сверху? Что будет с паролем на 100 или 1000 символов?

**Идеи для тестов:** пароль 7 и 8 символов; без цифры, без спецсимвола, без заглавной,
без строчной; очень длинный пароль.

---

## RI-005: Не описаны порог и срок блокировки аккаунта

**Где:** Swagger, `POST /users/login`; схема `UserResponse` (поле `failed_login_attempts`).

**Что не так:** на практике аккаунт блокируется после нескольких неверных паролей
(обнаружено при первом прогоне автотестов, см. `notes.md`). В документации не сказано:
- после скольких неудачных попыток блокируется аккаунт;
- на сколько блокируется и как разблокировать;
- сбрасывается ли счётчик после успешного входа.

В ответе есть поле `failed_login_attempts`, значит счётчик существует, но правила его работы не описаны.

**Вопрос:** какие правила блокировки правильные?

**Идеи для тестов:** N−1 неверных попыток, потом верный пароль → вход проходит;
N неверных попыток → блокировка; после успешного входа счётчик сбрасывается.

## RI-006: В Swagger для логина описан только ответ 200

**Где:** Swagger, `POST /users/login`, раздел Responses.

**Что не так:** в документации описан только успешный ответ `200` с токеном.
На практике API возвращает и ошибки, которых в документации нет:

| Ситуация | Код | Как обнаружено |
|---|---|---|
| Неверный email или пароль | `401` | автотесты |
| Аккаунт заблокирован после неудачных попыток | `423 Locked` | автотесты (`Account locked, too many failed attempts...`) |
| Аккаунт отключён | `403` | код API (`Account disabled`) |
| Недействительный или просроченный токен | `400` | код API (`Invalid or expired token`) |

**Вопрос:** нужно добавить в Swagger все коды ошибок логина с описанием, когда каждый
из них возвращается.

**Зачем это нужно:** клиент (сайт, мобильное приложение) должен знать, какие ошибки
показывать пользователю. Тестировщик — какие сценарии проверять.

**Идеи для тестов:** проверить каждый код из таблицы, включая отключённый аккаунт (`403`).

## RI-007: Неясно, включительны ли границы возраста 18 и 75

**Где:** Swagger, схема `UserRequest`, поле `dob`: «Must be a valid date between 18 and 75 years ago».

**Что не так:** из «between 18 and 75» непонятно, можно ли зарегистрироваться в день 18-летия
и в день 75-летия.

**Что показали автотесты:**
- в день 18-летия регистрация отклоняется (баг L-02);
- верхняя граница на деле 93 года, а не 75 (баг L-03).

**Вопрос:** границы включительные? По здравому смыслу человеку, которому сегодня исполнилось 18,
регистрация должна быть доступна.

---

## RI-008: Ограничения количества товара в корзине не задокументированы

**Где:** Swagger, `POST /carts/{id}` и `PUT /carts/{cartId}/product/quantity`, поле `quantity`.

**Что не так:** в документации указан только тип `integer`. На практике сервер принимает
от 1 до 99, а 0, −1 и 100 отклоняет с `422`.

**Что показали автотесты:** ограничение 99 действует на одну операцию, а не на итоговое
количество: повторным добавлением можно набрать 100 и больше (баг L-06).

**Вопрос:** 99 — это максимум для одной операции или для товара в корзине целиком?
Нужно описать ограничения в Swagger.
